## 1. 本版本交付什么

这一版把 P00—P03 的新引擎**真正接进可玩世界**。在此之前，新引擎是独立运行的原型；
玩家玩的仍是老引擎「每天按人口加一次钱、月底再结一次」。

| 类型 | 内容 |
|---|---|
| 计划 | `backend/systems/live_economy.py` — 动态标定层，把可玩世界的实际规模翻译成新引擎配置 |
| 编排 | `backend/core/simulation.py` — 重写月结接线，删掉按人口自动加钱 |
| 实体 | `backend/model/world.py` — 存档版本升到 3，新增账户簿、结算月份、待付施工款 |
| 实体 | `backend/model/transactions.py` — 新增 `HOUSING_SALE`、`CONSTRUCTION` 两个交易类别 |
| 持久化 | `backend/persistence/migrations.py`、`savegame.py` — 新增 v2→v3 迁移与账户簿校验 |
| 测试 | `tests/economy/test_live_integration.py` — 新增 24 项接入专项测试 |
| 测试总数 | **254 项**（接入前 230 项 + 本轮 24 项），全部通过 |

### 为什么需要「动态标定层」这一层

新引擎是按 **3000 人的参考城定值标定**的（六行业每月固定发 136,300 CR 工资）。
而玩家开局只有一百来人。把 3000 人的账本直接套上去，开局即破产。

所以 `live_economy.py` 按**人口比**统一缩放：

| 缩放什么 | 怎么缩 | 为什么 |
|---|---|---|
| 单价（税率、工资单价、租金单价） | **不动** | 单价是价格，改了就会改变经济规律本身 |
| 人数（就业、失业、收入层人数） | 按人口比缩放 | 人数跟着城市规模走 |
| 总量（营业额、采购、维修、拨款） | 按人口比缩放 | 让利润率、税率、储蓄率保持参考城的比例 |

市政采购、市政资本支出、业主维修、中央拨款这四项**不按人口比缩放**，
而是直接取配置里的实际值——因为月报口径用的是配置求和，实际付款用的是投入产出表，
两边必须逐分相等，否则市政支出报表会和账户里真实付出的钱差一个数。

## 3. 核心红线：按人口自动加钱是否真的没了

老引擎的写法是 `resident_funds += population × resident_income_per_person`，
账面上永远是正的，玩家永远不会缺钱。

新引擎下居民的钱**只能**来自账户间的真实转付。测试直接断言这一点：

| 检查项 | 方法 | 结果 |
|---|---|---|
| 余额变化 ≠ 人口 × 人均收入 | 对比首月余额增量与老引擎公式 | 不相等，红线守住 |
| 每笔居民收入都有本地付款方 | 遍历结算流水，核对付款账户 | 全部来自 firms / gov |
| 每笔居民支出都有本地收款方 | 遍历结算流水，核对收款账户 | 全部留在城内 |
| 市政现金 == 账户簿余额 | 月结后比对 | 分毫不差 |
| 居民资金 == 家庭 + 房东余额 | 月结后比对 | 分毫不差 |

首月居民收入的真实来源，逐笔可追溯：

| 付款方 | 收款方 | 金额（分） | 类别 |
|---|---|---|---|
| firms | households | 681,600 | wage 工资 |
| firms | landlord | 52,700 | commercial_rent 商业租金 |
| firms | households | 88,264 | dividend 分红 |
| gov | households | 89,000 | wage 公共部门工资 |
| gov | households | 17,900 | relief 救济金 |

居民支出去向：向 firms 采购 666,400 + 自住房屋维修 93,499，
向 gov 缴所得税 77,640 + 房产税 48,169，向 church 献奉 8,400。
**没有一分钱流向本地之外。**

## 4. 每笔现金变动是否都有付款方与收款方

月结是一次**全批次原子清算**：先把本月全部交易入队，算出每个账户的净变化，
任何一个本地账户变成负数就整批拒绝，**不留半个世界**。

这条底线不是靠说，是靠构造出来的。测试的做法是切断企业的外部订单与私人资本，
只留本地家庭那点消费，企业就必然付不出工资：

```python
sources["exports"] = 0            # 出口订单归零
sources["tourist_spend"] = 0      # 旅游消费归零
sources["private_capital"] = 0    # 私人资本注入归零
city.book[FIRMS].cash_cents = 0   # 企业期初余额清零
```

结果：

```text
拒绝结算: 账户 firms 余额不足：现有 0 分，需支付 416632 分
所有账户余额未变: True
```

**全部账户余额分毫未动**，证明是整批回滚而非部分落账。

## 6. 存档往返与幂等

| 检查项 | 方法 | 结果 |
|---|---|---|
| 存档读档后账户余额不变 | 存 6 个月 → 存 → 读 → 逐字段比对 | 完全一致 |
| 重读存档不会重复付款 | 存 3 个月 → 读 → 再触发同月结算 | 抛「本月经济结算已经完成」 |
| 账户簿损坏时拒绝读档 | 把某账户改成 −5 分 → 读档 | 抛「负余额」错误 |
| 旧存档 v1 / v2 仍可加载 | 走迁移路径 | 现金与居民资金原样保留 |

幂等由 `economy_month` 字段保证：同一个月只结算一次，读档重放不会再付第二遍钱。

## 7. 开发中发现并修复的缺陷

接入过程中发现并修复 6 个真 bug：

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 市镇现金凭空放大 100 倍 | 期初余额以 CR 计价，换算成「分」时又乘了一次 100 | 新增 `opening_in_cents` 开关，直接搬运存档分值 |
| 2 | 小镇教会收入占比是 18 倍 | 教会捐赠基数是硬编码常数 1200 CR，没有跟着缩放 | 改为可配置 `church_donation_base_cents` |
| 3 | 注入的配置被忽略 | `build_plan` 读的是全局常量，而不是传入的登记表配置 | 改为读 `registry.config` |
| 4 | 跨月消费反馈归零 | 每次月结新建收入层，「上期可支配收入」丢失 | 新增 `cohort_state` / `restore_cohort_state` 跨月接续 |
| 5 | 住宅成交与施工款绕过账本 | 直接改余额，没有付款方与收款方 | 改为账户间真实交易（家庭→gov、gov→world） |
| 6 | 市政采购报表与实际付款不符 | 报表按人口比缩放，付款按配置值，两者不等 | 两边统一引用 config 实际值 |

另有 2 个**测试设计错误**（不是产品 bug），一并记录：

- 原打算用「企业账户清零」构造破产，但实测发现企业在 168 人规模下**净流入为正**，
  清零后仍能完成结算（当月实收 173 万分真实货款覆盖 172 万分支出）。
  改为切断外部订单与资本金，才构造出真正违约的场景。
- 这恰恰证明了一件事：**企业的钱确实来自真实交易，不是期初余额硬撑**。

## 8. 已知边界与未完成项

这一版解决的是「接线」，不是「经济平衡」。以下问题**依然存在**，如实登记：

### 8.1 市政从第 12 月起每月净失血 1,315 分

| 项目 | 金额（分） |
|---|---|
| 市政收入合计 | 265,485 |
| 市政支出合计 | 266,800 |
| **净额** | **−1,315**（差 0.49%） |

已逐项比对参考城与接入城的收支比例（人口缩放系数 0.0933），
**每一项的偏离都在 5% 以内，最大偏离是房产税 −3,211 分**。

但房产税这一项经核算**并非缩放错误**：接入城 70 套住房评估值 437,500 CR，
按评估值比例应得房产税 481 CR，实际收入 481.69 CR，**完全吻合**。

真正的差异在住房**结构**：

| | 参考城 | 接入城 |
|---|---|---|
| 总套数 | 800 | 70 |
| 出租 | 600（75%） | 0 |
| 自住 | 150 | 70（100%） |
| 空置 | 50 | 0 |

接入城 70 套住宅评估值 437,500 CR，按评估值比例应得房产税 481 CR，实际收入 481.69 CR，**完全吻合**。

真正的差异在住房**结构**：

| | 参考城 | 接入城 |
|---|---|---|
| 总套数 | 800 | 70 |
| 出租 | 600（75%） | 0 |
| 自住 | 150 | 70（100%） |
| 空置 | 50 | 0 |

接入城的住宅全部是自住房、零出租，所以**没有任何租金收入**。
这是可玩世界的真实状态（玩家开局把住宅都设成自住），
但它让市政的房产税收入结构与参考城完全不同。

**这不是 bug，是待校准项。** 已登记为校准项 A-10。

### 8.2 人口迁徙已接线（本版新增）

上一版登记的第 5 项缺口「人口迁徙仍走老引擎、与新引擎脱节」已修复。

**修复前的问题：** `migrate()` 只改 `world.population` 一个数字。
新迁入的居民凭空出现、迁出的居民凭空消失——**人数动了，钱却一动不动**。

**修复方式：** 新增两类真实交易，每人按 `resident_savings_per_person`（800 CR）计价：

| 情形 | 付款方 | 收款方 | 类别 |
|---|---|---|---|
| 迁入 | 外部世界 | 家庭账户 | `migration_in` |
| 迁出 | 家庭账户 | 外部世界 | `migration_out` |

两条都是真实收付，**全城现金总量不变，只是换了个主人**。

实测（人口 168 → 280，每月经 14 人）：

| 月 | 人口 | 迁入 | households | world | 现金总量 |
|---|---|---|---|---|---|
| 1 | 182 | +14 | 14,543,366 | −1,284,460 | 18,377,464 |
| 8 | 280 | +14 | 23,164,959 | −10,629,340 | 18,377,464 |
| 60 | 280 | 0 | 27,352,207 | −23,780,140 | 18,377,464 |

现金总量 **60 个月分毫不差**，本地账户零负余额。

> 顺带修掉一个旧测试的盲点：`test_sale_money_moves_between_accounts_at_month_end`
> 原先断言「家庭账户余额会减少」，但迁入者带钱进来会抵消这笔变化。
> 该断言本就测错了对象——它想验证的是房款进了市政，现在改为比对市政账户与全城现金总量。

### 8.3 产能层与发展机制已接线，但尚未激活（见 0.7.0）

本版新增了产能公式（§4.1 Qcap）、企业进退（§9.1、§4.7）与发展层接线，
并新增存档版本 4 与 `migrate_v3` 迁移。

**当前状态：接线完成，但实际效果接近于零。** 对照实验（36 个月，仅差一个开关）：

| 月 | 关闭产能层营业额 | 开启产能层营业额 |
|---|---|---|
| 1 | 2,063,600 | 2,063,600 |
| 12 | 3,179,311 | 3,179,311 |
| 36 | 3,179,311 | 3,179,311 |

两条线完全相同。原因清楚：**六个产能因子里只有 F_worktime 有动态输入**，
而信仰比例 `opening_faith` 是常数，所以该因子恒为 1。

其余五个因子的输入源尚未落地：

| 因子 | 需要什么 | 当前状态 |
|---|---|---|
| F_labor | 就业与招聘真实波动 | ❌ 行业人数仍按人口比直接算出 |
| F_skill | 教育产出的技能结构（P07） | ❌ 无教育系统 |
| F_resource | 战略品库存（P06） | ❌ 无库存 |
| F_service | 供水供电等基础设施 | ❌ 恒为 1 |
| F_safety | 魔法师防御覆盖（P07） | ❌ 恒为 1 |
| F_worktime | 传教政策改变信仰比例 | ⚠️ 有公式，但信仰比例本身是常数 |

**这是接线完成、机制待激活，不是「已经会发展了」。**
按当前进度，城市仍然只是「人口增长带动营业额等比放大」，
而不是「玩家建设改变经济结构」。

| 项 | 数值 |
|---|---|
| 人口 182 → 280 | 1.54 倍 |
| 营业额同步 1.54 倍 | 说明营业额仍由人口决定，而非产能决策 |

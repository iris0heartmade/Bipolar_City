## 3. 范式对比：我们处在哪一格

这张表是本报告最重要的部分。**结论：我们的资金守恒路线比 Citybound 更严格，
不应被它的架构新颖性带偏。**

| 维度 | Citybound | isometric-city | **BIPOLE（现状）** |
|---|---|---|---|
| 经济本质 | 10 种资源的向量转移 | 人口 × 硬编码系数 | 货币账户双边清算 |
| 货币地位 | `Money` 只是 10 种 `Resource` 之一，与 `BakedGoods` 平级 | 无货币概念 | CR 为唯一计价单位，100 分/CR |
| 交易表示 | `give_to`/`take_from` 逐项加减 | 无 | `Transaction` 带付款方/收款方/来源 |
| 守恒保证 | **无**（两个方法各自加减，理论上可漏） | **无** | 清算引擎 + `check_conservation` |
| 数值类型 | `f32` 浮点 | 整数 | **整数分**，残差必须归属 |
| 时间粒度 | 实时 tick，每 4 秒更新，日内节律 | 回合制 | 日施工 + 每月一次结算 |
| 决策机制 | 匮乏驱动贪心（top 5 问题） | 固定公式 | 上期可支配收入 + 效用函数 |
| 税收/债务 | 完全没有 | 隐含在系数里 | 独立账户、税率政策、贷款台账 |
| 配置方式 | 查表 + DSL 化 | 硬编码 | 外部 JSON + 校准清单 |

**关键判断：** Citybound 追求的是"百万个体各自演算"，我们追求的是"一城资金来龙去脉可核账"。
两者解决的**不是同一个问题**。它没有税收、没有财政预算、没有债务、也没有任何守恒断言——
这恰恰是我们 P01 刚刚建立、且已有 130 项测试守护的能力。

> Citybound 作者 Alan Kay 曾批评初代 SimCity 是"反教育"的，因为它不透明。
> 我们的做法正相反：每一笔钱都能展开看到付款人、收款人与来源（见 `Settlement.trace`）。

## 4. Citybound 经济模型剖析

### 4.1 资源模型（`economy/resources.rs`）

```rust
pub enum Resource {
    Wakefulness,   // 清醒度（无形）
    Satiety,       // 饱食度（无形）
    Money,         // 金钱（与商品平级！）
    Groceries, Produce, Grain, Flour, BakedGoods, Meat, DairyGoods,
}

pub type ResourceAmount = f32;              // 浮点
pub type Inventory = ResourceMap<ResourceAmount>;
```

三点观察：
1. **无形与有形共用同一套机制**。睡眠、健康、劳动力与面包、牛奶走完全相同的加减逻辑。
2. **金钱被"商品化"**。`Money` 与 `BakedGoods` 在同一枚举里，商店收到 100 Money 和收到 100 面包
   在代码路径上**没有区别**。这让"营业额"和"收入"天然不分，我们的口径纪律它做不到。
3. **用 `f32`**。长期累积必然有浮点漂移。我们的整数分 + 残差归属是更严格的选择。

### 4.2 家庭共享性与供应商共享性分离

```rust
fn is_shared(resource) -> bool {        // 家庭内部共享？
    Wakefulness | Satiety => false,      // 清醒/饱食：每人私有
    Money | Groceries => true,           // 金钱/食品：家庭共享
}
fn supplier_shared(resource) -> bool {
    Money => false,                      // 供应商的金钱不共享
    Wakefulness | Satiety | Groceries => true,
}
```

**为什么重要：** `give_to_shared_private` 靠这两个函数决定资源落到"家庭共有池"还是"个人小金库"。
只做一套共享性判断就会出错——把 A 的清醒度加到 B 身上，或把供应商的钱混进家庭共有池。

> 对应我们的模块：这是 M03「职业与财产身份分开」的同源问题。房东身份（M05）也是同类陷阱。

### 4.3 交易意向与实际的双列表

```rust
pub struct Offer {
    pub max_users: u32,
    pub users: CVec<(HouseholdID, Option<MemberIdx>)>,       // 意向使用（尚未实际前往）
    pub active_users: CVec<(HouseholdID, MemberIdx)>,        // 实际使用者
    pub being_withdrawn: bool,                               // 撤出中，防止撤出时仍被使用
}
```

**这个设计和我们 M02 的「义务 vs 已付凭证」是同一个问题的两种解法。**
他们用两张表并存，我们用 `Transaction.status` 的 pending/settled 状态机。
`being_withdrawn` 标记尤其值得学：它承认了"撤回动作有延迟窗口"这个真实世界问题，
而不是假装撤回是瞬时的。我们的开发报价（M04）将来会遇到同样的窗口。

### 4.4 市场是按资源索引的中央注册表

```rust
pub struct Market {
    offers_by_resource: CDict<Resource, CVec<OfferID>>,
}
```

搜索是**异步双向**的：买家发起 `search` → 市场遍历该资源的所有报价逐个 `evaluate` →
通过 `expect_n_results` 登记预期返回数 → 结果齐了才回调。

> 我们的 P02 订单分配最多重分配 3 轮，是同步循环。他们的异步方案适合百万规模实时模拟，
> 我们只有 86 家聚合企业，同步更简单也更好调试。**不必照搬。**

### 4.5 通勤距离直接进入交易决策

```rust
const ASSUMED_AVG_SPEED: f32 = 10.0; // m/s
// 距离 → 时间 → 累加到交易耗时，且营业时间相应提前
new_deal.deal.duration += estimated_travel_time;
new_deal.opening_hours = new_deal.opening_hours.earlier_by(estimated_travel_time);
// TODO: adjust resources to incorporate travel costs   ← 作者自己留的坑
```

**注意最后那行 TODO：** 交通成本没有被折算成资源消耗，只影响了耗时。
这意味着"通勤"在他们的经济账里其实是**免费的**。我们的 M07 公式
`V=0.40*质量−1.10*(价格/类参考价)−0.07*分钟` 已经把分钟计入效用，**这一点我们做得更完整**。

## 5. 数值规划模板

这是老大要的「数值规划」重点。以下三张表都是**源码里的真实数值**，可直接借鉴其表达方式。

### 5.1 日内节律查表法（**已判定不适用于本项目**）

`family/mod.rs` 里用 12 个双小时的数组描述一天的需求强度，
查表方式 `lookup[hour / 2]`，索引 0 对应 0:00—2:00：

| 资源 | 0-2 | 2-4 | 4-6 | 6-8 | 8-10 | 10-12 | 12-14 | 14-16 | 16-18 | 18-20 | 20-22 | 22-24 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 清醒度 | 7 | 7 | 7 | 7 | 5 | 5 | 5 | 5 | 5 | 5 | 7 | 7 |
| 饱食度 | 0 | 0 | 5 | 5 | 1 | 5 | 5 | 1 | 5 | 5 | 1 | 1 |
| 金钱 | 0 | 0 | 3 | 3 | 5 | 5 | 5 | 3 | 3 | 1 | 1 | 1 |
| 食品杂货 | 0 | 0 | 4 | 4 | 1 | 4 | 4 | 4 | 4 | 4 | 0 | 0 |

读法很直观：夜里（0-4 点、22-24 点）除了清醒度全是 0，因为不消费；
早晨 4-8 与下午 14-18 是采购高峰；金钱需求在 8-14 点最高。

> **2026-10-13 修正：此表不适用于 BIPOLE。**
> 本项目日历为 30 天/月、12 月/年，经济按月结算，**不存在小时级消费节律**。
> 原稿曾提议照搬该表配置化到 P03/P07，经复核属生搬硬套，已作废。
> 真正的月度级节律见 [`calendar_v1.json`](../../data/economy/calendar_v1.json)：
> **月（经济结算）／季（日常议会与政策窗口）／年（报表、目标与借款额度重估）**三层，
> 该结构来自原设计稿 Q24/Q30/§9.2，非本报告发明。

### 5.2 配方式生产模型

`grocery_shop` 的 `decay` 函数（实际是产出与消耗）：

```rust
Groceries   += 500.0 × 1.00 × 天    // 每天产出 500 份混合食品
Meat        -= 500.0 × 0.20 × 天    // 消耗 100
DairyGoods  -= 500.0 × 0.10 × 天    // 消耗  50
Produce     -= 500.0 × 0.10 × 天    // 消耗  50
Grain       -= 500.0 × 0.05 × 天    // 消耗  25
Flour       -= 500.0 × 0.01 × 天    // 消耗   5
BakedGoods  -= 500.0 × 0.30 × 天    // 消耗 150
```

**所有量级统一挂在 `500.0` 这个基准产出上**，比例是干净的 0.2 / 0.1 / 0.1 / 0.05 / 0.01 / 0.3。
改产出规模只需改一个数字，配方比例自动缩放。

> **借鉴点：** 我们的 P06 战略资源表（粮食 250 产 / 300 用、煤 420/390）目前是绝对值，
> 缺少这种"基准产出 + 配方比例"的分层。**建议在 P06 引入 `base_output` + 配方系数结构**，
> 这样产能调整不会牵动整张表。

### 5.3 个体化随机系数的确定性种子（架构级借鉴）

```rust
let individuality = seed((self.id, i)).gen_range(0.8, 1.2);       // 成员 i
let individuality = seed((self.id, i, 1u8)).gen_range(0.8, 1.2);  // 同一成员的另一维度
```

**种子是结构化 ID 元组 `(household_id, member_idx)`，不是全局随机序列。**
这带来两个性质：同种子完全可复现；不同成员之间仍有稳定差异。
他们的衰减速率因此不是千人一面，但重载存档后每个人还是原来的脾气。

> **直接对应我们 M01 的硬要求：**「随机流按地图、报价、NPC、事件分域，防止动画/鼠标预览消耗经济随机数」
> 「禁止用跨进程不稳定的语言默认 `hash()` 当种子」。
> Citybound 用的是 `seed((id, idx))` 这种**元组哈希**——**恰好是设计规范点名要避免的做法**。
> 所以这条只能借鉴"分域"的思想，具体实现我们必须用显式的流 ID，不能直接抄。

### 5.4 行业方法论交叉印证

检索中反复出现两个概念，与我们的工作直接相关：

- **Taps 与 Sinks（来源与消耗）**：把游戏内货币的每一个产生点与消耗点列成表，
  两者速率失衡即通胀或紧缩。来源：
  [The Mathematics of Game Balance](https://departmentofplay.net/the-mathematics-of-balance/)、
  [How to Design a Game Economy](https://dev.to/hiroshi_takamura_c851fe71/how-to-design-a-game-economy-sources-sinks-loops-and-balance-j05)。
- **先模拟再计算**：纸面算不出的是长期漂移，必须跑长时间序列并按月追踪残差。
  同一来源建议用蒙特卡洛模拟覆盖多种行为路径。

我们的 `input_output_v1.json` 已经是一张完整的 Taps/Sinks 表，这是意外收获。

## 6. 可直接借鉴的六条

按对下一阶段的实际价值排序。

| # | 借鉴点 | 来源 | 落到我们的哪个阶段 | 动作 |
|---|---|---|---|---|
| 1 | ~~日内节律查表~~ | `family/mod.rs` | — | **作废**：本项目是月级经济结算，无小时节律。改用月/季/年三层（见 `calendar_v1.json`） |

| 3 | 供给方/消费方共享性分离 | `is_shared` / `supplier_shared` | M03 分群、M05 房东 | 资产归属与付款方分开建模，加断言防镜像 |

| 5 | 通勤时间进入交易代价 | `TripCostEstimator` | M07 消费选择 | **我们已做得更好**（计入效用而非仅耗时），保持 |
| 6 | 匮乏驱动排序决策 | `graveness` + top 5 | P03 居民需求 | 评估是否比效用函数更易解释与诊断 |

**查表法本身仍值得保留为"表达手段"**，只是时间粒度换成月/季/年：
`calendar_v1.json` 的月度评估参数（涨价 ±5%、调薪 ±3%、租金 ±3%、退出 3/6 月）
与年度事件表都是查表式配置，改平衡不用动代码。

**一条明确的反向结论：** 不借鉴 actor 模型与异步市场调度。
Citybound 为百万级实时模拟而生，我们是 3000 人月度结算。
引入 actor 架构只会增加调试成本，不解决我们的问题（我们的问题是**资金闭合**，不是**吞吐**）。

## 7. 反面教材

isometric-city 的经济核心（`src/lib/cityManager.ts`）：

```typescript
income += building.population * 0.5;  // Residential tax income
income += building.jobs * 0.3;         // Commercial/industrial tax
```

**税基 = 人口 × 0.5 + 岗位 × 0.3，硬编码在函数体里。**
没有账户、没有付款方、没有清算、没有税率政策、没有守恒检查。

> 这**正是**我们设计文档第 1 节批评旧原型的原话：「人口定额与商户定额」「`record()` 直接加钱」。
> 它说明我们的 P01 不是过度设计，而是这类玩法绕不开的地基。
> **这也反过来提醒：我们的 P02 接线时，绝不能为了省事退回按人口系数加钱的老路。**

## 8. 与现有守恒成果的交叉验证

用 Taps/Sinks 视角复查我们已交付的参考月：

| 项 | 金额（CR/月） | 说明 |
|---|---:|---|
| 外部流入（出口 + 游客 + 拨款） | 95,700 | 88200 + 5000 + 2500 |
| 外部流出（进口 + 利息） | −68,600 | 68000 + 600 |
| **外部净流入** | **+27,100** | 城市获得的净新增现金 |

内部 24 笔交易全部发生在本地账户之间，净额为零。
本地四主体现金变化之和（企业 +17312、居民 +8431、市政 +517、教会 +840）**恰好 = 27,100**。

**这说明我们的参考月不是一个"平衡的数字游戏"，而是一个真正的封闭资金系统。**
Citybound 做不到这一点——它的 `Inventory` 是各自加减的，跨主体对账无从谈起。

## 9. 对后续阶段的影响

| 阶段 | 本次调研带来的具体影响 |
|---|---|
| **P02** | 维持聚合同步结算路线，不引入 actor 模型。接线时严格禁止退回人口系数加钱。月结固定在第 30 日，只结算一次。 |
| **P03** | 消费节律与需求排序评估是否采用查表式配置；资产归属与付款方分离加断言 |
| **P04** | 开发报价引入"撤出中"延迟窗口，避免撤回被当成瞬时 |
| **P05** | 工资与价格收敛沿用现有 ±3%/±5% 纪律，作为月度评估项写入周期配置 |
| **P06** | 战略资源表重构为基准产出 + 配方系数；沿用 A-06 标记的矩阵补全流程 |
| **P07** | 公共服务的月度评估项接入周期配置；政策调整窗口对齐季度节拍 |
| **P08** | 年度周期承载 120 月长期压力测试与借款额度重估，是长期漂移的主要观测点 |
| **P10** | 季度议会、年度报告、约四年任期考核按月/季/年三层落地 |

**同时确认四件事不需要改：** 整数分而非浮点、账户双边清算、月度单次结算、无季节系统。
这四条是本项目区别于上述三个开源项目的根本选择，有测试守护，不动。

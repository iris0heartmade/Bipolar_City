### 0.2 已确认的框架前提（本方案的共同基础）

1. **本地城市现金不要求守恒。** 城市是海洋中的一只碗，可与海洋自由交换水。海平面近似恒定。引擎现状已经允许（实测首月本地现金 +27,100 CR，12 月累计 +292,294 CR），无需改行为，只需改语义与文案。
2. **只有碗与碗（城市与城市）之间的交易要求数量明确守恒。** 这一条**目前无法表达**，是多城阶段的前置工作（A-01～A-04）。
3. **月度结算一次报告；左侧参数代表该月发生的事情，主要受上月指标与突发事件指导。** 引擎已具备 `step()` 逐月推进与按 `start`/`end` 生效的冲击；GUI 未暴露（B-01～B-06）。
4. **守恒残差恒为 0 是双分录的结构恒等式，不是经济正确性的证据。** 它应保留为防回归护栏，但不应再作为验收的主要依据（A-06、F-01）。

## A 类：框架语义（碗–海洋）

### A-01 把 `external` 拆成 `ocean` 与 `city:<id>`【P0】

**位置**：`backend/systems/model_ledger.py:42`（`ACCOUNTS`）、`:47`（`kinds`）、`:48-50`（`Account` 构造）；`backend/systems/model_sim.py:56-58`（开账）

**现状**

```python
# model_ledger.py:42
ACCOUNTS = ('firms', 'households', 'government', 'church', 'external')
# model_ledger.py:48-50
self.book = AccountBook(Account(k, kinds[k.split(':')[0]], k,
                                None if k == 'external' else 'lab', cash_cents=v)
                        for k, v in values.items())
# model_sim.py:58
opening['external'] = -sum(opening.values())
```

全部 10 类对外科目（拨款、出口、游客、进口、外购、利息、本金、资本外逃、迁入积蓄、迁出带走）共用同一个 `external` 账户，且它的期初余额被定义为「本地合计的相反数」。

**问题**

1. 海洋、邻城、中央财政、游客、资本外逃混在一个余额里，无法分辨「卖给海洋」和「卖给邻城 B」。
2. `external` 余额被强制等于 −Σ本地，等于**把海洋也锁进了封闭世界**，海平面没有被建模。
3. 若就此外推到 N 座城市，会得到一个全局守恒约束——正是设计明确不要的东西。

**修改方案**

1. 账户分层，并区分**边界节点**与**对手方节点**：

```python
# backend/model/accounts.py:9-17
OCEAN = "ocean"     # 边界节点：city_id 为 None，免透支检查，可无限支付
PEER  = "peer"      # 对手方节点：city_id 指向邻城，受透支检查
LOCAL_KINDS = (HOUSEHOLD, FIRM, MUNICIPAL, CHURCH, LANDLORD, LENDER, PEER)
```

```python
# backend/systems/model_ledger.py:42
OCEAN_ACCOUNT = 'ocean'
def peer_account(city_id): return f'city:{city_id}'
ACCOUNTS = ('firms', 'households', 'government', 'church', OCEAN_ACCOUNT)
```

2. **关键语义区分**：`Account.is_external` 的定义是 `city_id is None`（`accounts.py:34-35`），而它同时被三处使用：

| 使用点 | 作用 | `ocean` | `city:<id>` |
|---|---|---|---|
| `model_ledger.py:80` | 付款方免余额检查 | 免检（海洋无限） | **必须检查**（见 A-02） |
| `settlement.py:122-123` | 跳过本地不透支校验 | 跳过（镜像账户） | **不跳过** |
| `accounting.py:71` | 排除在「未授权负余额」之外 | 排除 | **不排除** |

因此：
- `ocean` 保持 `city_id=None` → 三处行为全部维持现状，无需改动；
- `city:<id>` 必须带 `city_id=<邻城标识>` 且 `owner_kind=PEER` → 自动受透支检查。**这正是「城际交易数量明确守恒」的执行点**：邻城只能花掉它在本城账本里已经挣到的钱。
- 需要在 `AccountBook.add`（`accounts.py:63`）接受 `PEER` 种类，否则会抛「未知主体类型：peer」。

3. 期初余额改为显式配置，不再自动取反：

```python
opening[OCEAN_ACCOUNT] = 0        # 海洋不设余额约束，也不参与 local_leaves()
for city_id, value in p.get('trade.peer_opening_balances', {}).items():
    opening[peer_account(city_id)] = cr_to_cents(value)
```

4. 邻城透支上限（建议默认严格，即不允许赊账）：

| 参数 | 现值 | 建议值 | 理由 |
|---|---|---|---|
| `trade.peer_credit_limit_cents` | 不存在 | **0**，range `[0, 10000000]` | 0 表示「邻城只能花它在本城挣到的钱」，数量守恒最严格；放宽即为赊账 |

5. `local_total` 保持只统计本地叶子（现状已如此，无需改）。新增属性：

```python
@property
def ocean_net(self):  return self.cash(OCEAN) - self.opening_ocean
@property
def peer_net(self):   return sum(v - self.opening_peers[k]
                                 for k, v in self._peer_balances().items())
```

6. `_assert_invariants`（`model_sim.py:341`）的守恒断言改为分段表述：
```python
# 本地 ↔ 海洋：不要求守恒，只要求每笔都有对手方
if self.ledger.local_total - opening + self.ledger.ocean_net + self.ledger.peer_net != 0:
    raise GameError('双分录完整性断言失败（本地与对外账户未成对过账）')
```

**参数改动**

| 参数 | 现值 | 建议值 | 理由 |
|---|---|---|---|
| `trade.peer_opening_balances` | 不存在 | 新增，默认 `{}` | 邻城在本地账本中的初始应收/应付节点 |
| `trade.ocean_price_index` | 不存在 | 新增，默认 1.0 | 替代现由 `export_price_index`/`import_price_index` 兼任的"海洋价" |

**验收**

- [ ] `Ledger.ACCOUNTS` 中不再有 `external`；`ocean` 出现在账户表中。
- [ ] 首月 20 项基准（营业额 340,000、利润 42,400、税 5,088、税后 37,312、居民税前 173,300、可支配 157,131、财政收入 28,817、支出 28,300、结余 517、GVA 211,900、出口 88,200、进口 68,000、对外净流 27,100、利用率 80.00%、失业 9.09%）全部仍为 0.00% 偏差。
- [ ] 新增单测：本地现金从 726,562 CR 增至 780,274 CR（+53,712，三个月）时，`ocean_net` 相应变化，断言 `Δ本地 + Δocean + Δpeer == 0`。

**风险**：改动账户结构会波及 `_sync_cash`、`distribute`、`by_category`、`balances` 与全部引用 `'external'` 字符串的调用点（共 14 处，见 `artifacts/review_out5.txt` 第 6 节）。建议一次性替换字符串常量，不留别名。

### A-02 把免检余额规则收敛到单点【P1】

**位置**：`backend/systems/model_ledger.py:80`、`backend/systems/model_sim.py:147`

**现状**

```python
# model_ledger.py:80
available = amount if self.book[source].is_external else max(0, self.book[source].available_cents)
# model_sim.py:147
available = min(amount, self.ledger.cash(source)) if source != 'external' else amount
```

同一条「海洋可无限支付」的规则写了两遍。A-01 把 `is_external` 拆成 `ocean` 与 `city:<id>` 之后，两处若不同步修改就会出现「海洋免检、邻城也免检」的漏洞——**城际交易将因此凭空造钱**。

**修改方案**

1. 在 `Ledger` 上收敛为唯一入口：

```python
def available(self, source: str, amount: int) -> int:
    if self.book[source].owner_kind == OCEAN:      # 只有海洋免检
        return amount
    return min(amount, max(0, self.book[source].available_cents))
```

2. `Ledger.pay` 与 `EconomySimulation.distribute` 都改为调用 `self.ledger.available(source, amount)`。
3. 增加类型断言：`city:<id>` 账户必须 `owner_kind == PEER`，且 `is_external` 为 False。

**验收**

- [ ] 新增单测：`pay(source='city:cityB', ...)` 超过该节点余额时返回短付并写入 `shortfall`，不产生交易。
- [ ] **「免检」判定只出现在一处**：`grep -rn "amount if.*is_external\|!= 'external'" backend/` 结果为空，免检逻辑全部收敛在 `Ledger.available()` 内。
- [ ] `grep -rn "is_external" backend/` 的剩余结果仅限三处**语义正当**的边界节点用法，且全部只对 `ocean`（`city_id=None`）生效：`model_ledger.py` 的 `available()`、`settlement.py:122`（跳过本地不透支校验）、`accounting.py:71`（排除在负余额告警之外）。`accounts.py` 中的定义与 `AccountBook.add` 的种类校验保持不动。
- [ ] 新增单测：`city:<id>` 节点余额为负时，`Settlement.settle()` 抛 `InsufficientFunds`（证明它确实受不透支约束）。

**风险**：低。属于纯重构，行为在单城（无 `city:<id>` 节点）场景下完全不变。

### A-03 新增城市间交易的过账通道【P0，多城前置】

**位置**：`backend/systems/model_ledger.py`（新增），配合 A-01

**现状**：全项目只有一本 `Ledger`（一个城市）。没有任何跨账本的过账结构。

**问题**：设计要求「碗与碗之间的交易数量明确守恒」。当前若把邻城挂在对外账户上：A 城付款时 A 侧被扣，但**对方城市的账本里不会入账**，也没有任何机制校验对方是否付得起。结果就是数量不守恒。

**修改方案**

1. 新增轻量过账记录，不实现完整多账本，只保证可对账：

```python
@dataclass(frozen=True)
class PeerFlow:
    month: int
    direction: str          # 'out' 表示本城付出，'in' 表示本城收到
    peer_city_id: str
    category: str           # export / import / capital_flight / migration_out ...
    amount_cents: int
```

2. `Ledger` 增加 `self.peer_flows: list[PeerFlow]`，在 `pay` 中当 source 或 target 是 `city:<id>` 时自动登记一条。
3. 新增 `Ledger.peer_balance(city_id)`，语义为「该邻城在本城账本中的净额」，正值表示本城欠对方。
4. 新增对账函数：

```python
def reconcile_peers(self, other_ledgers: dict[str, 'Ledger']) -> None:
    """本城记录的 peer_flows 必须与对方账本的镜像记录逐笔相等，否则抛 GameError。"""
```

5. `SimulationResult` 增加 `peer_flows` 字段，供月报与存档持久化。

**验收**

- [ ] 单测：构造 A、B 两本 `Ledger`，A 向 `city:B` 付 1,000 CR，B 向 `city:A` 付 400 CR；`reconcile_peers` 通过，且 A 的 `peer_balance('B')` 与 B 的 `peer_balance('A')` 互为相反数。
- [ ] 单测：手工改坏一侧金额后 `reconcile_peers` 必须抛错。
- [ ] 单测：不存在「A 付出但 B 未入账」的状态（过账在同一事务内完成或在下一月强制对账）。

**风险**：本阶段只需"能对账"，不必实现真正的多城同时推进。建议把完整多城求解放在后续阶段。

### A-04 资本外逃与迁出携带的资金指向具体邻城【P1，多城前置】

**位置**：`backend/systems/model_dynamics.py:74`、`:163`

**现状**

```python
# :74  企业外迁
sim.ledger.pay(s.account, 'external', amount, 'capital_flight')
# :163 居民迁出
sim.ledger.pay(c.account, 'external', round(...), 'migration_out')
```

**问题**：在"多个碗"的设定下，外迁的企业和居民是**搬到别的城市**去了，那笔钱应落入某座具体邻城。现在流向海洋，导致"我的损失是邻居的收益"这一玩法无从体现；多城对账也会缺一半。

**修改方案**

1. `feedback.relocation_loss_months` 触发的企业外迁增加目的地选择：按各邻城的相对吸引力（沿用 C-06 的吸引力指标）加权随机或取最大值，写入 `city:<id>`。
2. `population.migration_out` 同理：按目的地吸引力分摊到若干邻城。
3. 新增参数：

| 参数 | 现值 | 建议值 | 理由 |
|---|---|---|---|
| `feedback.relocation_destination_mode` | 不存在 | `'highest_attractiveness'`，可选 `'weighted'`/`'ocean'` | 保留退路：单城阶段仍可全部流向海洋 |
| `feedback.migration_destination_mode` | 不存在 | 同上 | 同上 |

4. 单城阶段（`peer_opening_balances` 为空）自动退化为流向 `ocean`，保证现有场景结果不变。

**验收**

- [ ] 配置两个邻城时，外迁资金的 `peer_flows` 目的地非空，且总计等于外迁金额。
- [ ] 未配置邻城时，基准 120 月的全部指标与本方案实施前逐项一致（回归保护）。

### A-05 指标文案与健康区间改为开放经济口径【P2】

**位置**：`backend/model/indicators.py:181,190,192,213,218`

### B-01 `_apply_shocks` 每月重置参数，政策改动保不住【P0】

**位置**：`backend/systems/model_sim.py:23`（捕获 `_shock_defaults`）、`:184-195`（`_apply_shocks`）

**现状**

```python
# :23
self._shock_defaults = {k: deepcopy(self.params.get(k)) for x in self.shocks for k in x.get('overrides', {})}
# :184-186
def _apply_shocks(self):
    for key, value in self._shock_defaults.items():
        self.params.set(key, value, validate=False)
```

每月开头无条件把所有被冲击覆盖过的键恢复为初始值。

**实测**：冲击窗口为第 3–5 月。第 8 月税率 = 0.08（已恢复）。第 8 月手动改为 0.15，`step()` 后第 9 月**又回到 0.08**。

**问题**：设计要求"左侧参数代表这个月发生的事情，受上月指标指导"。这个实现只支持"初始值 + 冲击窗口"，无法表达"玩家在第 8 月改了税率并保持下去"。**它是两侧顺序迭代的头号阻塞项。**

**修改方案**

1. 把"基准值"与"冲击覆盖"分离，改为边界切换：

```python
def _apply_shocks(self):
    active = {k: v for sh in self.shocks
              if sh['start'] <= self.month <= sh.get('end', self.month)
              for k, v in sh.get('overrides', {}).items()}
    # 只在进入/离开窗口时写值，窗口内不重复写
    for key in set(self._shock_defaults) | set(active):
        if key in active:
            self.params.set(key, active[key], validate=False)
        elif self._shock_owner.get(key) == 'shock':        # 上一月由冲击写的
            self.params.set(key, self._baseline[key], validate=False)
        # 其余情况（玩家手动改过）：不动
    self._shock_owner = {k: 'shock' for k in active}
```

2. 新增 `_baseline` 快照（构造时的参数值）与 `_manual_overrides` 集合；`set_policy()` 写入时登记到 `_manual_overrides`，冲击撤销时跳过这些键。
3. 冲击进入/离开的月份写入 `self.events`，便于月报显示"本月政策恢复"。

**验收**

- [ ] 单测：`step()` 到第 8 月 → 手动改 `tax.income_flat_rate = 0.15` → 连续 `step()` 到第 12 月，每月读取该参数均为 0.15。
- [ ] 单测：冲击窗口（第 3–5 月）内该参数取冲击值，第 6 月恢复为手动值 0.15 而非初始值 0.08。
- [ ] 基准 120 月（无手动改动）的全部指标与修改前逐项一致。

**风险**：需要小心处理"冲击覆盖的键恰好也是玩家改过的键"这一情形。建议优先级为：手动改动 > 冲击窗口 > 基准值，并在 GUI 上提示冲突。

### C-01 扩张门槛高于基准利用率，正反馈没有点火源【P0】

**位置**：`backend/systems/model_dynamics.py:92`、`:97`；参数 `business.expansion_utilisation_min`、`capacity.reference_utilisation`

**现状**

```python
# :92  扩张岗位

# :97  新企业开业
if s.utilisation >= p.get('business.expansion_utilisation_min') and s.investment_reserve >= setup > 0:
```

参数默认值：`capacity.reference_utilisation = 0.80`、`business.expansion_utilisation_min = 0.85`。

**实测**：基准 120 月 —— 新开企业 0 家、破产 0 家、外迁 0 家、净迁入 −30 人；产能利用率从 80.00% 单调降到 74.27%。

**问题**

设计稿 §4.2 说 80% 是"便于扩张的校准选择"，§4.7 却要求扩张需"前 3 月平均产能利用率 > 85%"。基准利用率低于扩张门槛，且模型里**没有任何能推高利用率的驱动力**（出口固定、人口不动），因此扩张条件永远不成立。设计稿承诺的正反馈闭环（订单↑→利润/现金↑→投资/新企业→招聘→收入/迁入/需求↑）在基准下**从未启动过**。

**修改方案**（建议三条一起做）

1. **引入外部需求增长项**，让海洋侧的胃口随时间或随竞争力变化——这是"多个碗"的自然结果（世界在增长，城市靠抢份额增长）：

| 参数 | 现值 | 建议值 | 理由 |
|---|---|---|---|
| `trade.external_demand_growth_monthly` | 不存在 | **0.002**（约 2.4%/年） | 基准下温和增长；设 0 可回到旧的静态基准 |
| `trade.external_demand_growth_cap` | 不存在 | 2.0 | 外部需求最多涨到初始的 2 倍，防止长期失控 |

2. **增设分级扩张门槛**，把"温和发展"与"高速扩张"分开：

| 参数 | 现值 | 建议值 | 理由 |
|---|---|---|---|
| `business.expansion_utilisation_min` | 0.85 | **0.85 保持不变**（作为"高速扩张"档） | 尊重设计稿 §4.7 |
| `business.expansion_utilisation_mild` | 不存在 | **0.75** | 新增"温和扩张"档，低于基准 80%，使基准城市具备起步能力 |
| `business.expansion_utilisation_min_range` | `[0.75, 0.95]` | `[0.70, 0.95]` | 给温和档留出下探余地 |

3. 温和档的扩张幅度受限：`addition *= 0.5`，高速档维持全额。这样保留"利用率越高扩张越快"的设计意图。

| 6,000 | 3,000 | 619,694 | 88,200 | 90,579 | +3,398 |

60 月后市政现金：人口 500 → **1,100,550 CR**；人口 3,000 → 34,375 CR。

**问题**：海洋对本城的购买量是固定名义额，与本城规模无关；而本城向海洋的购买随规模缩放。结果**缩城成为最优策略**。注意总产能只有 72,823 CR 的城市仍能出口 85,200 CR——因为价格上限 3.0 允许企业抬价去承接这笔固定名义订单（`model_dynamics.py:134`）。这直接摧毁了经营游戏的核心动机。

**修改方案**

把外部需求挂到本城实际产出/产能上，并保留"多个碗"的竞争语义：

```python
# 本城可承接的外部订单 = 基础需求 × 产出能力比 × 竞争力
output_ratio = sum(s.revenue_cents / max(s.price, 0.01) for s in sim.sectors) / \
               cr_to_cents(sum(s.base['revenue'] for s in sim.sectors))
exports = cr_to_cents(p.get('trade.exports_base')) \
        * p.get('feedback.export_demand_multiplier') \
        * output_ratio ** p.get('trade.export_output_elasticity')
```

**参数改动**

| 参数 | 现值 | 建议值 | 理由 |
|---|---|---|---|
| `trade.export_output_elasticity` | 不存在 | 新增 **1.0**，range `[0, 2]` | 1.0 = 出口与产出同比例；0 = 退回旧的固定年金行为（保留做对比） |
| `trade.exports_base` | 88,200 | 保持不变 | 首月仍须对账 88,200 |

**验收**

- [ ] 上表四点的 `total_exports` 随规模单调上升；人口 500 点的出口 ≤ 人口 3,000 点的 50%。
- [ ] 四点的 `net_external_flow` 不再随缩城而上升（人口 500 点净流应低于人口 3,000 点）。
- [ ] 首月对账：出口仍为 88,200 CR、对外净流仍为 27,100 CR。
- [ ] 缩城测试：`population.start` 从 3,000 降到 1,000，60 月后 `municipal_cash` 低于基准。

### C-06 迁徙必须响应税负与收入【P0】

**位置**：`backend/systems/model_dynamics.py:138-147`

**现状**

```python
# :144
target = min(sim.housing_units * p.get('housing.household_size'),
             round(jobs / max(0.01, participation * reference_employment)))
# :147
delta = max(-cap, min(cap, target - total))
```

目标人口 = `min(住房容量, 2 × 岗位数)`，与收入、税负、房租、公共服务、危险度**完全无关**。

**实测**：所得税从 8% 提到 20%，120 月后人口仍为 3,000（变化 0%）；失业率仍为 9.09%；破产 0 家；市政现金从 34,375 CR 涨到 971,392 CR。企业税 25% 再多加 12 万 CR。

**问题**

设计稿 §5.2 定义了五点吸引力指标 `U_z = 0.30×实际可支配收入指数 − 0.25×住房负担指数 − 0.15×通勤指数 + 0.15×公共服务指数 − 0.15×危险指数`，**未实现**。在"多个碗"的框架下，这个指标正是把居民和资本推向别的碗的压力阀。缺了它，加税没有任何代价，财政政策失去全部张力（违反设计稿 §7.1 与 TEST-B）。

**修改方案**

1. 聚合版吸引力指标（无空间模型时，通勤项以"就业匹配度"替代，并显式登记为新增校准假设）：

```python
income_index  = (per_capita_disposable / baseline_per_capita_disposable)
rent_index    = (rent_cents / baseline_rent_cents) / max(0.01, income_index)
tax_index     = 1 - (effective_tax_burden / baseline_tax_burden - 1)
service_index = school_coverage * 0.5 + (1 - magic_risk) * 0.5
danger_index  = magic_risk
attract = (w_income * income_index - w_rent * rent_index - w_tax * tax_index
           + w_service * service_index - w_danger * danger_index)
attract = max(0.0, min(2.0, attract))
target = round(min(housing_capacity, jobs_derived) * attract)
```

2. 迁出通道必须走通：`attract < 1` 时 `target < 当前人口` → 净迁出，且迁出者按 `migration_savings_per_person` 带钱离城（`model_dynamics.py:163` 已有此逻辑）。

**参数改动**

| 参数 | 现值 | 建议值 | 范围 | 理由 |
|---|---|---|---|---|
| `migration.attract_weight_income` | 不存在 | **0.30** | `[0, 1]` | 设计稿 §5.2 |
| `migration.attract_weight_rent` | 不存在 | **0.25** | `[0, 1]` | 设计稿 §5.2 |
| `migration.attract_weight_tax` | 不存在 | **0.20** | `[0, 1]` | **设计稿未列，属新增校准假设，需登记** |
| `migration.attract_weight_service` | 不存在 | **0.15** | `[0, 1]` | 设计稿 §5.2 的公共服务项 |
| `migration.attract_weight_danger` | 不存在 | **0.15** | `[0, 1]` | 设计稿 §5.2 |
| `migration.attract_floor` / `_cap` | 不存在 | **0.5 / 1.5** | — | 防止单月人口剧烈跳动 |
| `migration.reference_disposable_per_capita` | 不存在 | **52.38** CR | — | 首月基准人均可支配收入，用于归一化 |

**验收**

- [ ] 首月人口仍为 3,000，净迁入 0（吸引力 = 1）。
- [ ] 所得税 8% → 20%，120 月后人口下降 ≥ 3%（当前 0%）。
- [ ] 房租上调 50%，120 月后人口下降 ≥ 1%。
- [ ] 学校覆盖率从 80% 降到 40%，120 月后人口下降 ≥ 1%。
- [ ] 新增单测：`attract=0.5` 时目标人口为基准的一半，且迁出者带走现金，`net_external_flow` 相应下降。

**风险**：这是本方案中影响面最大的一条，会改变全部 15 个场景的终局。必须在 C-03、C-04、C-05 之后做，否则规模效应与吸引力效应会互相掩盖。

### C-07 价格水平加锚【P1】

**位置**：`backend/systems/model_dynamics.py:111-135`

**现状**

```python
# :129-134
demand_ratio = max(0.01, (s.revenue_cents + s.unmet) / max(1, s.capacity_units * s.price * p.get('capacity.reference_utilisation')))
step = p.get('market.price_adapt_k') * math.log(demand_ratio)
step += p.get('market.price_adapt_k') * imported_pressure * s.base['input_cost'] / s.base['revenue']

# :135  CPI 为基准营收加权的行业售价

```

价格只对相对供需（`demand_ratio`）反应，没有任何绝对水平锚。工资按 `CPI ** wage_cpi_exponent`（0.7）挂钩，形成通缩正反馈。

**实测**：CPI 1.000（第 1 月）→ 0.988（12 月）→ 0.842（60 月）→ 0.703（120 月）。同期基准价实际产出 +16.5%，名义 GVA −31.4%，人均名义可支配收入 52.38 → 39.11 CR。

**问题**

1. 名义指标全面误导：玩家会看到城市"越来越穷"，而实物产出在增长。
2. 固定名义义务相对变重：债务利息（600 CR/月）、中央转移、救济、教会捐赠上限、最低工资（40 CR）都不随 CPI 调整。
3. 所有健康区间都是名义口径，会随时间漂移。

**修改方案**

1. 引入外部价格锚（海洋价近似恒定，正好充当锚）：

```python
anchor = p.get('market.price_anchor_k') * math.log(p.get('trade.ocean_price_index') / max(0.01, s.price))
step += anchor
```

| 参数 | 现值 | 建议值 | 范围 | 理由 |
|---|---|---|---|---|
| `market.price_anchor_k` | 不存在 | **0.02** | `[0, 0.1]` | 0 = 退回无锚行为 |

2. 削弱工资的通缩传导：`labour.wage_cpi_exponent` 由 0.70 降到 **0.35**（设计稿 §4.6 写的是 0.70，需在统一决策表登记覆盖）。
3. 给 CPI 设健康区间并让 GUI 标色：`healthy=(0.92, 1.08)`。

**验收**

- [ ] 基准 120 月：`cpi` 落在 `[0.92, 1.08]`。
- [ ] 基准 120 月：名义 GVA 与实际产出的变化方向一致（当前相反）。
- [ ] 首月 CPI 仍为 1.000，首月对账不受影响。
- [ ] `price_anchor_k = 0` 时结果与修改前可比（保留对照）。

**风险**：会与 C-02 的产能-需求平衡相互作用。建议先做 C-02（消除过度投资），再做 C-07（加锚），否则锚会掩盖失衡。

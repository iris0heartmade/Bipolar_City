# BIPOLE 分阶段开发计划

版本：1.0｜日期：2026-10-13｜作者署名：iris0heartmade

**目标：** 保留可玩的魔导城市原型，先建立可核账的一城经济，再逐步实现双路径住宅、逐店经营、公共服务、城际市场及长期国家沙盒。

**架构：** 单一 Python 权威模拟（通俗比喻：全城共用一本正式账本）＋ FastAPI 命令入口＋原生 JavaScript/Canvas 展示。经济按月事务结算，日时钟只推动施工和月界，不开第二套经济循环。

**技术与范围：** 沿用现有代码栈；本文件是项目级阶段计划，列出明确交付、文件方向与验收门槛。列为“拟新增”的代码和测试尚未实现；阶段执行时再拆分为具体提交，不将本文误当成已运行的完整程序。

## 1. 输入与当前差距

依据：[原设计总纲](../01_原始输入/bipole世界观下开罗式模拟经营游戏的设计稿.txt)、[经济输入 V1.0](../01_原始输入/Bipole_城市经济系统开发输入_V1.0.txt)、本轮用户确认的住宅双路径与随机差异。规则细节统一引用 [模块详细设计](../03_设计规范/游戏模块开发要求与详细设计.md)。

| 内容 | 当前 0.2.0 原型 | 目标要求 | 处理阶段 |
|---|---|---|---|
| 画面/建造 | 魔导工业 UI、28×28 模板、格子施工 | 保留表现；新增 64×64 校准城、可建道路和用地规划 | P04、P08 |
| 居民收入 | `resident_income_per_person` 每月直接增加余款 | 企业/政府真实发薪，股息与租金有付款人 | P01—P03，必须替换 |
| 企业 | 只计集市商户数和岗位 | 企业现金、工资、订单、投入、利润、税与投资 | P02、P05 |
| 地方税 | 人口定额与商户定额 | 所得、正利润、房产评估值对应税基 | P02、P05 |
| 住房 | 政府直建，出售/公共出租，分户产权 | 政府直建或规划后私人开发，两条路径都可选 | P04 |
| 房租/维护 | 市政侧有分类账，私人房东账缺失 | 租户、私人业主、维修企业均有真实对手账户 | P01—P04 |
| 人口 | 总人口直接与岗位比较 | 就业＋失业＋非劳动力＝人口，通勤与迁入有约束 | P03 |
| 战略资源/贷款 | 未实现 | 库存、实际运输、债务本金与利息 | P05—P06 |
| 宗教/教育/安全 | 尚无实际系统，灯光属演出 | 轻量宗教四效应、教育延迟、道路可达防御 | P07 |
| 存档 | 版本 2 与已知版本 1 迁移 | 账户、交易、报价、合同、随机状态和模型版本 | P01 起，P08 完整切换 |

历史记录中的 59 项测试和原型 M1 验收只证明旧范围；不能用它们声称已实现经济输入的 TEST-01—20。当前不是“只差银行”，应先解决资金来源和全城闭合。

## 2. 总路线与依赖

```text
P00 统一要求与校准输入
└─ P01 账户、交易、外部边界
   └─ P02 六行业聚合经济与首月闭合
      └─ P03 居民分群、就业、预算与消费
         └─ P04 道路空间、政府直建/私人开发与报价
            └─ P05 逐店企业、政策与基础贷款
               └─ P06 战略资源、5—8 NPC 城市与贸易
                  └─ P07 公共设施、教育、魔法安全与宗教
                     └─ P08 长期经济可玩版、校准与兼容
                        └─ P09 科技/人物、银行与可恢复金融风险
                           └─ P10 国家政治、条件事件、二十年评价
```

UI、存档和回归随各阶段同步交付，不另排到最后。P07 的接口在 P02 就预留，动态机制在 P07 接入；P02 的教会与公共工资基准是校准账户，不等于先完成宗教玩法。最初外部市场可聚合为一个真实边界账户，不必等 NPC 城市做完才获得可验证的订单。

阶段以验收通过为边界，不虚报固定工期。执行顺序为当前会话顺序推进；本计划不自动派发其他聊天或子代理。多人实时同步不是 P10 的默认交付，须后续独立立项。

| 阶段 | 对应原书 | 能交付给玩家/开发者的成果 |
|---|---|---|
| P00—P03 | 经济输入 M0 的基础 | 不依赖画面的真实单城月报与资金闭合 |
| P04—P07 | 经济输入 M1 逐步细化 | 双路径住宅、企业与空间市场、公共服务和国家市场 |
| P08 | 经济输入 M1 整体验收 | 可长期玩且可诊断的经济版本 |
| P09—P10 | 经济输入 M2＋总纲长期目标 | 科技、人物、银行风险、议会与国家事件 |

模块：[M01 世界时钟](../03_设计规范/游戏模块开发要求与详细设计.md#m01)、[M02 账本](../03_设计规范/游戏模块开发要求与详细设计.md#m02)、[M21 存档](../03_设计规范/游戏模块开发要求与详细设计.md#m21)。

- [x] 定义金额、交易类别、付款人、收款人、来源义务、商品/库存引用和月度唯一 ID。
      交易 ID 由「月＋来源义务＋支付段」确定性生成，同一义务重复提交自动幂等。
- [ ] 实现预留、缩量、欠付/取消和一次清算；同一 `source_ref` 不能由交易阶段和财政阶段重复支付。
      已完成：预留与释放、按来源核销部分履约、一次清算、任一付款方不足整批回滚、重复义务幂等。

      旧原型的 `record()` 仍在 `systems/finance.py` 服役，需在 P02 接线时替换。
- [ ] 将月度变化提交为原子快照；暂停不结算，重复月请求不再次生成工资/税。

**输出：** 开发诊断页可展开一笔交易的付款人、收款人、类别与来源；不先堆完整市场动画。

## 5. P02：单城聚合经济闭环

**目标：** 先以六行业聚合企业证明工资、消费、采购、利润、税、房租和外部流量闭合。

模块：M02、M05—M07、M09、M10、M14 的基准账户与 M22 验收。拟新增：`backend/model/economy.py`、`backend/core/monthly.py`、`backend/systems/production.py`、`markets.py`、`property_income.py`、`reports.py`。拟测试：`tests/economy/test_reference_month.py`、`test_cash_conservation.py`。

- [x] 配置参考需求：家庭消费、业主维修、公共采购、资本投资、企业互购、出口与游客。
- [x] 按实际付款记录营业额/投入；雇主支付 121900 私企工资，市政支付 14400 公共工资。
- [x] 私企利润扣折旧但现金流不再扣折旧；正利润税后才分红。
- [x] 记录 28200 住宅租金和 9500 商业租金流向家庭业主，业主支付 16700 维修。
- [x] 按所得、正利润与评估值计算税；教会捐赠实际减少教会储备。
- [x] 外部出口、进口、游客、中央拨款、外部利息各有边界账户；战略品金额此时只作为订单组成预留，没有重复加一笔贸易额。
- [x] 显示营业额、利润、财政结余、居民可支配收入和 GVA（通俗比喻：扣掉重复中间交易后的新增价值），不能互相替代。

**精确基准：** 私企工资 121900；税前利润 42400；企业税 5088；家庭净现金 +8431；企业 +17312；市政 +517；教会 +840；全城与外部净流量均 +27100；GVA 与支出法均 211900 CR/月。详见 [数值表](../03_设计规范/游戏模块开发要求与详细设计.md#calibration)。

**本轮实际结果：** 月度引擎 `core/monthly.py` 按 calendar 的 15 步跑出参考月，上述全部基准由引擎计算命中，
没有一处从配置读回来自己验证自己。参考月恰有 24 笔交易，每笔都有付款方与收款方；
同一月份重复提交或读档重放不产生二次付款。

**已知边界（已在 P03 解决）：** 固定配置下居民每月净流出 12569 CR，第 12 月末储蓄接近耗尽，第 13 个月将因余额不足而整批被拒。
这是「消费不随收入变化」的结果，不是引擎缺陷——已由 P03 的预算反馈解决，见 [0.5.0 验收](../04_验收记录/验收记录-0.5.0.md)。
该行为曾写成测试钉死，P03 已把它改写为「24 个月不再耗尽」的验收断言。

**尚未完成：** 订单分配、价格形成与生产调度仍取自已校准的流量表，本轮不做供需重分配；
市政单边 `record()` 与旧 `simulation.py` 的时钟接线留待后续阶段。

**验收：** 经济输入 TEST-01—11、14、15、17、18 在实际交易引擎通过；纯算术核对只算输入检查，不算引擎通过。关闭外部流量的场景，不得仅靠居民购物产生全城新钱。

## 6. P03：居民分群、就业与消费

**目标：** 从“人口给收入”过渡为“劳动合同与资产收入形成下一期预算”。

模块：M03、M06、M07。已新增：`backend/model/households.py`、`backend/systems/labor.py`、`backend/systems/consumption.py`；调整 `backend/core/monthly.py` 与 `backend/model/economy.py`。已交付测试：`test_population_identity.py`（16）、`test_labor_market.py`（16）、`test_consumption_budget.py`（20）。

- [x] 按片区、收入、技能聚合；职业与财产身份分开，特殊角色也不得双计人口。
- [x] 记录 1500 就业、150 失业、1350 非劳动力的参考人口；不把 3000 人全部当岗位需求。
- [x] 招聘由企业/公共设施实际岗位、工资报价和可达劳动者决定，工资有付款账户。
- [x] 消费预算使用上期可支配收入和可动用储蓄，预留基本房租/食品/燃料；本期新工资进入下一期预期。
- [x] 低收入和高收入篮子分别配置，避免所有家庭使用统一食品比例。
- [ ] 净迁徙受住房、岗位、真实收入、通勤、服务与危险约束，普通月最多当前人口 1%；携带人口、技能、信仰与真实资金。（配置公式与月度 1% 上限已写入 `labor_consumption_v1.json` 的 migration 段，引擎尚未调用；P03 本轮不实现迁徙）

**验收：** 人口三项恒等；同一人不被两个企业录用；欠薪或低工资影响实际钱包和下一期需求；提高标价而预算不变时不能无限提高营业额。迁入现金从外部/其他城市扣转，不能漏计净流入。

**本轮实际结果：** 人口三项恒等在构造时硬校验，分群合计精确等于 3000/750/1500/150/1350；基准无空缺时新招 0 人、失业 150 人保持待业，零售业扩张 20 岗时新招 20 人且失业降至 130；消费首月精确 119,000、第 2 月起稳定在 119,270.37。

**顺带修复的 P02 缺陷：** 分层所得税只算出高收入层那一份，导致市政月结余 −10043 并在第 10 个月破产；房东净房产收入只进不出，导致住户钱包每月净流出 12569 并在第 13 个月破产。两处均已修复，36 个月连续演化守恒且不破产，P02 的 14 项基准仍逐项精确命中。详见 [0.5.0 验收](../04_验收记录/验收记录-0.5.0.md)。

## 7. P04：道路空间与双路径住宅

**目标：** 玩家可自由选择政府直建，或规划后由开发商投资；用时、费用和建成效果有可复现的随机差异。

模块：M04、M05、M08、M15。拟新增：`backend/model/plots.py`、`development.py`、`backend/systems/developers.py`、`roads.py`、`quotes.py`、`spatial_cache.py`；调整 `placement.py`、`construction.py`、`housing.py` 与前端建造工具。

- [ ] 支持 64×64 新场景与 28×28 原型模板并存，不拉伸旧档；固定地形、地标和国家位置保持种子可复现。
- [ ] 建筑多格占地、旋转入口、路网连通、分区规划和相邻地块解锁统一后端验证。
- [ ] 政府直建由市政预算/获批贷款付款，可持有出租或真实出售；规划住宅地由开发商自行评估回报、资金与道路后施工。
- [ ] 报价包含投资方、实际付款方、工期、建设/基础设施费用、品质和维护结果；随机边界来自外部配置。
- [ ] 同一地块、方案、报价周期的预览/取消/重放不刷新随机结果。确认后保存合同和报价样本；加载不重抽。
- [ ] 私人建设资金由开发商/投资方支付，市政只承担明确规划/基础设施/补贴；没有合格开发商时显示未入驻，不生成空免费楼。
- [ ] 私人租户入住无需购买整套房；待售空房、可出租空房、公房和自住房的容量分别计算。
- [ ] 真实道路最短路用于商户选择与通勤；道路重建只失效相关空间缓存，不运行全部行人车辆寻路。

**验收：** 两种路径从 UI 到账户、施工、产权、入住和存档均真实可玩；重复预览不能刷优质报价；同种子恢复一致；承诺资金不足不开工或按合同挂起；已有住户缺少替代房时不强制清空。

## 8. P05：私营企业、行政政策与基础贷款

**目标：** 将六行业聚合细化为参考场景约 86 家企业，建立利润驱动的开业、招聘、扩张与退出。

模块：M06、M07、M09、M10。拟新增：`backend/model/firms.py`、`loans.py`、`backend/systems/firm_decisions.py`、`taxation.py`、`credit.py`；前端增加企业档案、税政和债务面板。

- [ ] 逐店模型拆分后的行业总量与聚合基准一致，不凭拆分多出企业/家庭现金。
- [ ] 开业需要规划准入、路网、预期利润率 >6% 和至少 1.5 月固定支出资金；使用过去 3 月历史，不能预知未来。
- [ ] 连续 3 月不能支付必要费用或连续 6 月税前亏损才进入退出程序，保留欠薪/债务/资产处置。
- [ ] 扩张需订单、钱、工人及前 3 月平均有效产能利用率 >85%；投资真实付款给设备/施工卖方。
- [ ] 工资目标每月收敛 25%，普通月涨跌不超过 ±3%；税率权限/冷却与成本在 UI 可读。
- [ ] 先接外部国有银行的政府贷款；放款增加现金和本金，利息为费用，偿还本金为融资现金流。
- [ ] 初始本金 60000、月息 1%、剩余 12 月宽限，宽限期只付息；宽限后按显式摊还配置验收，不暗设期限。
- [ ] NPC 初期可仅用已明确的自有资金；其借款与居民按揭在 P09 扩展，不先放任无限信贷。

**验收：** 亏损不征负利润税；股息按现金截断；高税率反馈税基而非永远线性赚更多；设备资本支出和折旧现金口径分离；第 13 月本金偿还不污染经营费用；失败企业可恢复或渐进退出。

## 14. 阶段验收、风险与下一任务

每阶段交付：代码/配置 → 自动测试 → 真实场景 → UI/报表与存读档 → 中文验收记录 → CHANGELOG → 更新本计划状态。没有需要浏览器的纯账本阶段，先做无 UI 验证；可玩阶段不能以看到页面代替功能完成。

| 风险 | 处理方式 | 下一步 |
|---|---|---|
| 初期原型工资/商户税无完整付款链 | 暂标旧原型范围，P01—P02 重建真实账户 | P01 优先于银行美化 |
| 两份文件旧阶段重名 | 新阶段只用 P00—P10 | 历史 M1 不混入新进度 |
| 首月合计可对但长期现金漂移 | 交易单一清算、残差按月追踪 | P02 起每月守恒，P08 长期压力测试 |
| 随机报价可被免费重刷 | 稳定报价键、限幅、确认锁定、保存样本 | P04 同格重放/旋转/取消测试 |
| 原型到 3000 人/86 企业直接扩容 | 先聚合，再空间，再逐店 | P02→P03→P04→P05 |
| 微观企业数据缺少全部初始现金/订单分配 | P00 显式校准，保留来源和舍入约定 | 不把基准合计当假交易 |
| 旧币种与新账户不能无损映射 | 保存原文件，不默认等值换币 | P01 制定兼容，P08 完整切换 |

**下一项实际开发工作：** 完成 P00 的可运行参考场景配置，随后实施 P01 的 `Account / Transaction / settlement` 与对应守恒测试；不是直接在旧工资模型上再添加银行。
